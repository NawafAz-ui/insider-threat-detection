Integrated Test Report

This report shows whether all parts of the prototype work together: the log files, the detection engine, the run worker, MongoDB, the API and the dashboard in a browser. It lists each test case with its result, the problems found with the corrective actions, and what was not checked.

Insider Threat Detection prototype, ITE499A Capstone Project A, Group 7. Test run on 16 November 2026. Plan: docs/INTEGRATED_TESTING_PLAN.pdf. Result: 10 of 10 cases passed.

1. How the test was run

One command, python scripts/integration_test.py in the backend folder, starts every part and runs all cases in a fixed order. It uses the real MongoDB 7 server with a separate scratch database (itd_integration), so the main database is not touched, and the scratch database is deleted at the end. The parts started are the API, a second API that requires HTTPS, the run worker, the dashboard and a headless Chrome browser. Three kinds of data are used: generated data in the CERT layout (60 users, 80 days, 8 insiders), the SPEDIA prototype dataset (246 sessions), and five small hand-made folders with faults or edge cases. Each case compares what happened with what should happen and saves both in a results file.

4. What was not checked

  • HTTPS in a real browser with a certificate. IT4 only checks that plain HTTP is refused.
  • The secure MongoDB set-up with separate accounts for the engine and the API.
  • The hosted language model with a real key. The assistant answered from its offline template.
  • The original CERT r4.2 data. Only generated data and SPEDIA were used.
  • Many users at the same time, browsers other than Chrome, and phone-size screens.
  • Speed on other machines. All times were measured on one laptop with small data.
